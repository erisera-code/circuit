On styling by structure, not by class.

Most frameworks make you add a class to every element. This engine takes the opposite stance: it reads the tree and infers intent. The same <article> is prose in a column, but becomes a card when it is nested in a list. A button as the last child of a form reads as the primary action. A <header> inside an article becomes a byline.

The premise

Binding styles to element identity and position is only reliable now because modern CSS finally makes structural inference predictable: :has() for parent-aware rules, :where() for zero-specificity, @layer for ordered cascade, @property for typed tokens, @container for context-aware components, and color-mix() for derived color.

Each design you can switch to above is an instance — a complete restyling of this very document through custom properties and layout overrides. The markup never changes. That is the whole demonstration.

Note. This callout is inferred from role="note" — tone follows the role, not a class.

The tag name is the hook. Where it sits decides what it means.

— the engine, on itself

The grammar

The engine's binding vocabulary is small. Element type plus tree position covers the great majority of intent; a tiny set of escape hatches covers the rest.

/* the safe, zero-specificity pattern */
:where([data-engine]) {
  & :where(article) {
    & > :where(header) { /* byline row */ }
    & > :where(p:first-of-type) { /* lede */ }
  }
  & :where(ul:has(> li > article)) { /* card grid */ }
}
article
Prose in a column — or a card, when nested in a list.
header
Byline when inside an article; site banner when a top-level child.
aside
A callout or marginal note, offset from the main flow.
details
A disclosure widget with a CSS-drawn rotating caret.
form > button:last-child
The primary call to action — accent treatment by position.
<de-grid>
An escape hatch: a layout primitive with no semantic HTML equivalent.

The materials

A figure with a caption, and a list of articles that the engine turns into a responsive card grid automatically — equal heights, hover lift, container queries.

  • Foundation

    A scoped reset, typed @property tokens, an @layer spine, and @supports gates that no-op gracefully.

  • Structure

    Flow rhythm, sections, cards inferred from lists, grids, split layouts, and a sidebar shell.

  • Components

    Dialogs, popovers, menus, tabs, tooltips, badges, progress, breadcrumbs — all inferred.

The sequence

How the cascade resolves a single element, from least to most authoritative:

  1. The browser's user-agent stylesheet sets defaults.
  2. The engine's reset, scoped under [data-engine], normalizes them.
  3. Tokens (@layer de.tokens) define the design vocabulary.
  4. Base, structure, and component layers bind by element + position.
  5. The instance layer remaps everything for a distinct design.
  6. Host styles, unlayered or in a later layer, always win.

The interaction

Native disclosure, a form whose last button becomes primary, a metered value, and a popover — all styled from semantics alone.

How do instances switch without a build step?

The data-instance attribute selects a token-and-layout pack. Because every engine selector is wrapped in :where(), an instance overrides cleanly without specificity wars — and the markup is untouched.

The composition

Regions nest. This section keeps the page's design; the one below carries its own data-instance, and because every layout and effect rule is @scoped, the nearer design wins inside it while tokens keep flowing. The grid after it reads an integer from data-cols through typed attr(), and the last card re-hues the accent with data-hue.

A terminal inside the page

Same markup, different region: section[data-instance="terminal"]. Its palette is a light-dark() pair forced to the dark side by data-theme on this element alone.
